- [x] ~~Empty prefix/exclude lists not omitted at SDK-command layer — **Python, JS** (`EMPTY-FILTER`, §16)~~ **DONE** — Python (`http_data_source.py`, both `get_config`/`get_experiment_config`) now `prefix=prefix_filter or None`; JS (`http-data-source.ts`, both commands) now `prefix: prefixFilter?.length ? prefixFilter : undefined`. - [x] ~~No single-in-flight-refresh guard (SHOULD) — all four~~ **DONE (§17):** concurrent `refresh()` callers now coalesce onto one in-flight refresh in all four languages, so an OnDemand TTL-expiry burst causes one fetch, not N. Java: shared `Future` + owner-cancels-on-timeout, outcome recorded on the worker. Python: shared `asyncio` task (`_run_one_refresh`) awaited via `shield`. JS: shared self-clearing `Promise` (`runOneRefresh`). Rust: `futures_util::future::Shared` over a `Weak`-capturing boxed future (required `SuperpositionError: Clone`). Compiles/typechecks in all four; full test runs still blocked by the stale-native-lib env issue.
- [x] ~~Remote identifier inconsistent across paths (§14)~~ **DONE — standardized on `""` everywhere.** Canonical: an absent targeting key is represented as an empty string, uniformly, because the local core's `eval_config(..., targeting_key: String)` is a required string (established by `VAR-KEY`) — so `""` is the one representation the whole codebase can share; the server buckets `""` the same as absent. All six remote sites now send `""`: Rust `.identifier(targeting_key.unwrap_or_default())` (resolve + variants), Python `identifier=targeting_key or ""`, JS `identifier: targetingKey ?? ""`, Java `inputBuilder.identifier(Optional.ofNullable(merged.getTargetingKey()).orElse(""))` (resolve + variants). All compile. (An earlier attempt to *omit* empty was wrong — it split from the local `""` convention; reverted.)
- [x] ~~Python: `fetched_at` has no "fallback to now"~~ **NOT A BUG (verified, no change).** On the exact response types the provider uses — `GetConfigOutput`/`GetExperimentConfigOutput` — `last_modified: datetime` is **non-optional (schema-required)** in both the venv and repo SDK, so `response.last_modified` is always present; Rust likewise has it non-`Option`. The earlier "Python nullable" read was a mis-attributed grep (the `datetime \| None` hits were on *other* model classes). JS's `?? new Date()` is a **TypeScript-type artifact** (TS codegen marks the field optional, so the `??` is only there to satisfy the compiler assigning to a non-optional `fetchedAt: Date`), not a runtime gap. A defensive Python+Java fallback was briefly added, then reverted as dead code. (§2.2)
- [x] ~~Python: init `global_context = context` with no null→empty default~~ **DONE** — `local_provider.py:115` now `context if context is not None else EvaluationContext()`, matching JS (`?? {}`) / Java (`!= null`) and Rust (non-`Option` by type). - [x] ~~JS: GENERAL error message inserts `typeName`~~ **DONE (Option B — `typeName` is canonical).** The `typeName` was already in every language's *log* line; the divergence was only in the *returned* `errorMessage`, where JS included it and Rust/Python/Java didn't. - [x] ~~JS list-query interceptor~~ — **RESOLVED (verified 2026-07):** the JS smithy-typescript SDK *does* serialize list `@httpQuery` members (`Aws_restJson1.ts:1124-1135` etc. — `prefix`/`exclude_prefix` arrays → `.q(query)`). - [x] ~~Java: `SuperpositionError` has no `toString()`~~ **DONE (Option C).** Investigation showed only Python matched the old literal `"{CODE}: {message}"`; Rust (thiserror phrase), JS (`Name [CODE]: msg`) and Java (class-name, no code) all rendered idiomatically-but-differently.
